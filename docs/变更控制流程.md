# 变更控制与版本发布流程

> 对应 `docs/医疗器材合规优化方向.md` **第五章「配置管理」**、**第三梯队第 18 项**。
>
> 目标：任何一行代码的改动都能回答「为什么改、谁批准的、测了什么、从哪个版本到哪个版本」。

---

## 1. 版本号规则（语义化版本）

```
主版本.次版本.修订号    例：1.1.0
```

| 位置 | 递增条件 | 本项目示例 |
|------|---------|-----------|
| **主版本** | 不兼容的接口 / 数据格式变化（如历史文件格式不兼容） | 1.x → 2.0.0 |
| **次版本** | 向后兼容的功能新增（如新增技术报警） | 1.0.0 → 1.1.0 |
| **修订号** | 向后兼容的缺陷修复（不改变行为契约） | 1.1.0 → 1.1.1 |

**单一真源**：版本号只在 `CMakeLists.txt` 的 `project(vital_monitor VERSION x.y.z)` 定义，
`main.cpp` 通过编译宏 `VITAL_MONITOR_VERSION` 读取。
**禁止**在其它文件硬编码版本字符串。

## 2. 变更分级

| 级别 | 判定 | 审批 | 验证要求 |
|------|------|------|---------|
| **A 类（安全相关）** | 触及 `AlarmDetector`、`AlarmBanner`、`UserRole`、`FileIntegrity`、`SampleData` 的语义 | 至少 1 名评审人 + 逐条对照 `docs/危害分析与FMEA.md` | 全部自动化测试 + 目视回归 + 更新 FMEA |
| **B 类（功能）** | 新增通道、新面板、新的数据字段 | 1 名评审人 | 自动化测试 + 需求追溯矩阵更新 |
| **C 类（文档/样式）** | 注释、README、颜色微调 | 自审 | 构建通过 |

## 3. 变更流程（6 步）

```
1. 提出变更请求（CR）
   - 填写：背景 / 变更内容 / 影响文件 / 分类（A/B/C）/ 关联需求编号
2. 风险影响分析
   - A 类必须回答：会不会引入新的危害？现有控制措施是否仍有效？
   - 更新 docs/危害分析与FMEA.md（新增行或修改残余 RPN）
3. 实现
   - 小步提交，提交信息格式见 §5
   - 同步更新文件头注释（说明「为什么」）
4. 验证
   - cmake --build --preset mingw-debug
   - ctest --test-dir build/vscode-mingw-debug --output-on-failure
   - A 类额外：手工回归 §6 清单
5. 文档同步（缺一不可）
   - docs/CHANGELOG.md
   - docs/需求追溯矩阵.md（新增/修改需求的验证列）
   - README.md（若涉及能力描述）
   - docs/SOUP清单.md（若升级第三方）
6. 发布
   - 更新 CMakeLists.txt 的 VERSION
   - 打 tag：vX.Y.Z
   - 写发布说明（改了什么 / 已知问题 / 升级注意事项）
```

## 4. 问题解决流程（缺陷处理）

```
发现缺陷
  ├─ 能复现？ → 否：记录环境与日志，标记「待复现」
  └─ 是
      ├─ 是否安全相关（影响报警 / 数据真实性）？
      │    ├─ 是 → 立即评估是否需要回滚或热修复；A 类流程
      │    └─ 否 → 常规流程
      ├─ 写一个**失败的**测试用例（回归守护）
      ├─ 修复
      ├─ 测试转绿
      └─ 记录到 CHANGELOG 的「修复」段
```

> 「先写失败用例再修复」是本项目已执行的实践：例如
> `alarm_state_test` 用例 9（伪迹门控）在实现前先确认会失败，
> 修复后成为永久回归守护。

## 5. 提交信息规范

```
<类型>: <一句话说明>

背景：为什么需要这次改动（问题 / 需求编号）
改动：关键实现点（2~5 条）
验证：跑了什么（构建 / ctest / 手工回归项）
```

**类型**：`fix` / `feat` / `refactor` / `docs` / `test` / `chore`

示例：

```
fix: 修复告警「只报一次」的锁存缺陷

背景：优化文档 2.2 指出 highLatched 一旦置位，患者持续越限也只报一次
改动：改为状态机 + alarmRepeatMs 周期重报；超时未确认自动升级
验证：ctest 全绿（alarm_state_test 用例 1/2/3）
```

## 6. 发布前回归清单（A 类必做）

| # | 检查项 | 通过标准 |
|---|--------|---------|
| R-1 | 构建无警告新增 | `cmake --build --preset mingw-debug` 成功 |
| R-2 | 单元测试全绿 | `ctest` 显示 `100% tests passed` |
| R-3 | 启动自检 | 状态栏显示「自检：通过」 |
| R-4 | 演示模式标识可见 | 顶部橙色标识始终存在 |
| R-5 | 报警声光 | 制造越限 → 横幅变色闪烁 + 提示音 |
| R-6 | 持续报警 | 持续越限 → 按间隔重复提示，不停止 |
| R-7 | 确认后重报 | 点确认 → 声音停 → 条件仍成立时再响 |
| R-8 | 暂停到期恢复 | 暂停 → 显示倒计时 → 到期恢复报警 |
| R-9 | 报警列表排序 | 高危在前，显示持续秒数与确认状态 |
| R-10 | 越权拦截 | 切「查看者」→ 改报警限被拒 + 日志有记录 |
| R-11 | 二次确认 | 管理员改报警限 → 弹出「旧值 → 新值」 |
| R-12 | 导出 + 清单 | 导出数据 → 生成 `.sha256` 文件 |
| R-13 | 篡改检出 | 手改 CSV 一个数字 → 导入被拒绝 |
| R-14 | 部分损坏容错 | 删掉几行内容 → 导入提示「部分恢复」 |
| R-15 | 审计校验 | 点「校验审计」→ 显示校验通过 |

## 7. 回滚策略

- **代码**：`git revert` 到上一个 tag（本项目要求每次发布打 tag）。
- **数据格式**：历史文件 v2 加载端兼容 v1，**禁止**写出不兼容格式而不升主版本。
- **配置**：本项目配置不落盘，回滚无残留。
