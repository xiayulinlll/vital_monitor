## 二、逐文件说明

### 2.1 `CMakeLists.txt` — 构建定义

**解决什么问题**：一个工程产出两个可执行文件，共享业务层代码，避免"测试代码复制一份"导致的行为漂移。

| 目标 | 类型 | 源文件 | 链接 |
|------|------|--------|------|
| `vital_monitor` | WIN32 GUI 程序 | 全部 22 个源文件 | Qt6::Core / Gui / Widgets |
| `alarm_state_test` | **控制台**程序 | 测试 + `SampleData.h` + `ChannelConfig.*` + `AlarmDetector.*` | Qt6::Core / Gui |

**关键决策与原因**：

1. `set(CMAKE_AUTOMOC ON)` 等三件套：让 CMake 自动跑 `moc/uic/rcc`，源文件里不用手写 `#include "xxx.moc"`。
2. **`alarm_state_test` 显式关掉 AUTOMOC**（第 96–101 行）：
   ```cmake
   set_target_properties(alarm_state_test PROPERTIES
       WIN32_EXECUTABLE FALSE     # 保留控制台，测试输出可见
       AUTOMOC OFF AUTOUIC OFF AUTORCC OFF)
   ```
   原因：该测试不含任何 `Q_OBJECT` 类，无需 moc；而在某些受限环境下 `moc_predefs` 探测（`g++ -dM -E`）不可用会导致构建失败。
3. `WIN32_EXECUTABLE TRUE`（主程序，第 108 行）：抑制 Windows 控制台黑窗。
4. `windeployqt` POST_BUILD（第 113–125 行）：自动把 Qt 运行时 DLL 拷到 exe 同级目录，双击即可运行。
5. **测试与主程序共用同一批业务层源文件**（第 76–80 行），而不是编译成静态库——少一层间接，同时保证"测的就是跑的那份代码"。
6. `enable_testing()` + `add_test()`：接入 CTest，`ctest` 可直接跑。

**运行方式**：
```cmd
cmake --build build\vscode-mingw-debug
build\vscode-mingw-debug\alarm_state_test.exe   && echo PASS   (退出码 0 = 全部通过)
```

### 2.2 `src/main.cpp` — 程序入口（23 行）

**解决什么问题**：启动 QApplication，并**注册跨线程信号槽要传递的自定义类型**。

```cpp
qRegisterMetaType<ChannelSample>("ChannelSample");
qRegisterMetaType<SampleFrame>("SampleFrame");
qRegisterMetaType<AlarmEvent>("AlarmEvent");
qRegisterMetaType<QVector<ChannelConfig>>("QVector<ChannelConfig>");
```

**为什么必须有这四行**：采集线程与主线程之间用 `QueuedConnection`，Qt 会把参数**拷贝进事件队列**。对于非 Qt 内建类型，必须先用 `qRegisterMetaType` 注册，否则运行时会在控制台打印
`QObject::connect: Cannot queue arguments of type 'SampleFrame'` 并**静默丢帧**——这是 Qt 多线程最经典的坑。

> 注意 `Q_DECLARE_METATYPE`（在 `SampleData.h` 中）解决的是**编译期**类型系统登记，
> `qRegisterMetaType` 解决的是**运行期**队列拷贝，两者缺一不可。

`setOrganizationName` 用于让 `QSettings` 有正确的注册表路径（本版本未用持久化设置，但为后续留口）。

### 2.3 `src/data/SampleData.h` — 全项目共享的数据结构（130 行，纯头文件）

**解决什么问题**：定义四个跨层传递的核心类型，并集中定义报警配色。它是全项目的"合同"。

| 类型 | 用途 | 关键字段 |
|------|------|---------|
| `ChannelSample` | 单通道一次采样 | `channelId`、`value`、`quality`(SQI 0~1)、`invalid` |
| `SampleFrame` | 一次采集的多通道快照 | `sampleIndex`(时间轴坐标)、`timestampMs`、`channels`、`deltaMs`、`droppedFrames` |
| `AlarmEvent` | 一条告警事件 | `sampleIndex`、`channelId`、`level`、`category`、`state`、`highLimit`、`value`、`limit`、`text` |

**三个精妙设计点**：

1. **`sampleIndex` 与 `timestampMs` 分离**（第 35–36 行）
   - `sampleIndex` 是**严格单调递增的整数**，作为绘图 X 轴的唯一坐标 → 避免系统时钟回拨（NTP 校时）导致曲线倒退。
   - `timestampMs` 只用于**显示与存档**。
   - 这是医疗设备"时间轴必须单调"的正确做法。

2. **`AlarmEvent::conditionKey()`**（第 88–94 行）— 把"同一通道同一方向"的告警归并为**同一个跟踪对象**：
   ```cpp
   QString conditionKey() const {
       return QStringLiteral("%1/%2/%3")
           .arg(static_cast<int>(category)).arg(channelId)
           .arg(highLimit ? "HI" : "LO");
   }
   ```
   没有它，持续越限会每帧新增一条告警，列表瞬间爆炸。

3. **`alarmIndicatorColor()`**（第 119–128 行）— IEC 60601-1-8 色码的**单一真源**：
   | Level | 颜色 | 含义 |
   |-------|------|------|
   | `Escalated` / `Critical` | `#D32F2F` 红 | 高优先级（危及生命） |
   | `Warning` | `#D69A09` 琥珀 | 中优先级 |
   | `Info` | `#2A9EB0` 青 | 低优先级 |

   被 `AlarmBanner`、`VitalValuePanel`、`TrendChartWidget` **三处共用**。旧实现中曲线三角用 `#E74C3C`、报警条用另一套色，医护人员会把同一次告警误判成两个事件——集中定义彻底消除该风险。


### 2.4 `src/data/VitalSignSimulator.h/.cpp` — 生理信号模拟器（后台子线程）

**解决什么问题**：没有真实监护硬件时，**在生产环境中持续产出逼真且可控的多通道体征数据**。

**线程模型**：对象被 `moveToThread(workerThread)`，`QTimer` 在子线程触发 → 只在子线程内生成数据，**绝不触碰 UI**，通过 `frameReady` 信号（自动 QueuedConnection）投递。

**信号 / 槽**：
```cpp
signals: void frameReady(const SampleFrame &frame);   // 数据出口
         void statusText(const QString &text);         // 状态文本
slots:   void start(int intervalMs = 100);  // 10 Hz
         void stop(); void updateConfigs(...); void reset();
```

**数据生成算法**（`nextValueFor`，第 131–190 行）——四层叠加，模拟真实波形形态：

| 组成 | 代码 | 作用 |
|------|------|------|
| 缓慢随机游走 | `m_current[idx] += (center - m_current[idx]) * 0.02` | 均值回归，防止长期漂出量程 |
| 周期分量 | `qSin(m_phase[idx]) * span * 0.03` | 呼吸/心跳节律感 |
| 随机噪声 | `(rand - 0.5) * span * 0.01` | 传感器噪声 |
| 偶发越限脉冲 | `m_spikeCountdown` 触发，`span * 0.18` | **制造告警场景**用于演示/测试 |

**三个"必须实现"的合规逻辑**：

1. **丢帧检测**（第 86–97 行）— 用**实际时间差**判定：
   ```cpp
   frame.deltaMs = nowMs - m_lastTickMs;
   if (frame.deltaMs > expected * 3 / 2)              // 超过 1.5 倍周期
       frame.droppedFrames = qMax<qint64>(1, (frame.deltaMs / expected) - 1);
   ```
   注意：`Timer` 是软件定时器，`Qt::PreciseTimer` 也不保证准时；必须用**真实时钟差**而非"数帧数"。

2. **SQI 劣化模拟**（第 163–185 行）— 随机进入 20 帧的"低质量窗口"，让 SQI 落在 `[0.05, 0.30]`（低于告警抑制阈值 0.35），同时给读数叠加更大噪声（因为信号差时读数**本来就不可信**）。

3. **`s.invalid = (quality < 0.15)`**（第 124 行）— 区别于"质量差"与"完全测不到"：前者显示 `SQI xx%`，后者显示 `信号无效`。

**已知限制（诚实说明）**：
- `int m_spikeCountdown[4]` 是**硬编码 4 通道**，与 `m_configs.size()` 不同步。当前默认恰好 4 通道，若增删通道会越界风险。**建议改为 `QVector<int>`**（见审核报告 R-3）。
- 模拟的是**数值型趋势数据**，不是 ECG/PPG 原始波形采样。

### 2.5 `src/core/RingBuffer.h` — 线程安全定长环形缓冲（136 行，模板）

**解决什么问题**：项目难点 ② —— **7×24 小时运行，内存占用必须恒定**。

**核心机制**：
```cpp
void append(const T &value) {
    QWriteLocker locker(&m_lock);
    if (m_data.size() >= m_capacity) m_data.removeFirst();   // 满则淘汰最旧
    m_data.append(value);
}
```

**为什么用 `QReadWriteLock` 而不是 `QMutex`**：写入在主线程（每帧 1 次），读取在绘图/状态栏（可能多次并发）。读写锁允许**多个读者并发**，只有写时独占。

**接口清单**：

| 方法 | 用途 |
|------|------|
| `append(T)` / `append(QVector<T>)` | 单条 / 批量写入（批量减少加锁次数） |
| `snapshot()` | 全量拷贝快照（线程安全） |
| **`rangeByKey(from, to, keyOf)`** | **局部重绘的核心**（第 97–114 行） |
| `latest()` / `oldest()` | 取最新/最旧 |
| `setCapacity(int)` | 动态调整容量，缩容时丢弃最旧 |

**`rangeByKey` 为什么重要**：绘图只需要**当前视口**内的点。用 `std::lower_bound` 二分定位起点（数据天然按 `sampleIndex` 递增），复杂度 O(log n + k)，避免每帧遍历全部 6 万条记录。

```cpp
auto beginIt = std::lower_bound(m_data.cbegin(), m_data.cend(), from,
    [&keyOf](const T &item, quint64 v) { return keyOf(item) < v; });
```

**性能注意（可优化点）**：`QVector::removeFirst()` 是 **O(n) 搬移**。对本项目规模（6 万帧）每帧搬移约 6 万个元素，实测可接受，但追求极致应改为**环形下标（head/tail 指针）实现**——见审核报告 R-3。

### 2.6 `src/core/ChannelConfig.h/.cpp` — 通道配置与患者预设（277 行）

**解决什么问题**：集中管理"每个通道叫什么、什么颜色、量程多少、阈值多少、报警多急"，并提供**患者类型预设**。

#### 数据结构 `ChannelConfig`（`ChannelConfig.h` 第 46–95 行）

| 字段组 | 字段 | 说明 |
|--------|------|------|
| 标识 | `id` / `name` / `unit` / `color` | 通道身份 |
| 量程 | `minValue` / `maxValue` | 曲线 Y 轴范围 |
| 一级阈值 | `alarmLow` / `alarmHigh` / `hasLowAlarm` / `hasHighAlarm` | 一般越限 |
| **二级阈值** | `alarmLow2` / `alarmHigh2` / `hasSecondaryLow` / `hasSecondaryHigh` | **危及生命** |
| **优先级** | `alarmPriority`（Low/Medium/High） | IEC 60601-1-8 三级 |
| **时基参数** | `alarmDelayMs` / `alarmEscalateMs` / `alarmRepeatMs` | 去抖 / 升级 / 重报 |
| 显示 | `visible` / `sampleIntervalMs` | |

**两个关键的枚举与语义**：

```cpp
enum class PatientType { Adult, Pediatric, Neonate, Custom };
enum class AlarmPriority { Low, Medium, High };
```

`clamp()` 函数带有一条**刺眼的警告注释**（第 87–88 行）：
> ⚠️ 该函数会丢失越限信息，**不可用于告警判断路径**；告警判断必须使用未经裁剪的原始值。

这是真实踩过的坑：模拟器输出经过 `clamp()` 后，数值永远撞不到阈值边界之外，告警会漏报。

#### `loadDefaults()`（第 31–100+ 行）— 四通道默认配置

| id | 名称 | 量程 | 一级阈值 | 二级阈值（危及生命） | 优先级 | 特殊 |
|----|------|------|---------|---------------------|--------|------|
| 0 | 心率 HR | 40–180 bpm | 60 / 110 | 50 / 150 | Medium | — |
| 1 | 血氧 SpO2 | 85–100 % | 94（仅下限） | 88 | **High** | `delay=500ms`, `escalate=5s` |
| 2 | 呼吸率 RR | 0–40 rpm | 8 / 24 | 5 / 32 | Medium | — |
| 3 | 体温 Temp | 34–42 ℃ | 35.5 / 37.5 | 35 / 39 | Low | — |

**注意 SpO2 的特殊配置**：血氧是最关键的生命参数，所以①一级就是高优先级 ②报警延时压到 500ms（其他 1000ms）③升级时限压到 5s（其他 10s）。这是**按临床紧急度差异化配置**的体现，不是拍脑袋。

#### `loadProfile()`（第 175–226 行）— 患者类型剖面

**解决什么问题**：新生儿心率 120–160 bpm 是正常的，套用成人上限 110 会**持续误报**——这是临床上真实的重大风险源。

```cpp
const QHash<QString, ProfileEntry> &table = profileTable();
const QString key = QString("%1/%2").arg((int)type).arg(c.id);   // 如 "2/0" = 新生儿/HR
```

`profileTable()` 定义三档剖面（成人/小儿/新生儿）× 4 通道。

**两大设计亮点**：

1. **`overwriteCustom` 保护**（第 177–189 行）：已手工改为 `Custom` 的通道**默认不覆盖**，避免抹掉医生的手动设置。调用方能显式传 `true` 强制覆盖（`MainWindow::onPatientTypeChanged` 就是这么做的，因为用户是主动切的患者类型）。

2. **二级阈值按比例平移**（第 207–222 行）——**这是全项目最值得讲的一段**：
   ```cpp
   const double span = qMax(1.0, e.maxValue - e.minValue);
   if (e.hasLow)  c.alarmLow2  = qMax(e.minValue, e.alarmLow  - span * 0.10);
   if (e.hasHigh) c.alarmHigh2 = qMin(e.maxValue, e.alarmHigh + span * 0.20);
   ```
   为什么不能给新生儿和成人用同一个绝对危险值？因为**危险界值应随生理基线平移**。这里取"一级阈值到量程端点距离的 10%/20%"，保证新生儿与成人的危险线各自合理，同时用 `qMax/qMin` 夹在量程内。

#### 进程级患者类型单点真源（第 256–277 行）

```cpp
namespace {
PatientType &globalTypeStorage() { static PatientType s_type = PatientType::Adult; return s_type; }
}
PatientType ChannelConfigManager::globalPatientType()        { return globalTypeStorage(); }
void ChannelConfigManager::setGlobalPatientType(PatientType) { globalTypeStorage() = t; }
```

**为什么需要**：`ChannelConfigPanel`、`AlarmBanner` 等多个控件都要知道"当前是成人还是新生儿"，但只有 `MainWindow` 持有 `ChannelConfigManager` 实例。用函数内 `static` 变量做单点真源，避免把管理器指针层层下传，也保证 UI 显示一致。

### 2.7 `src/core/AlarmDetector.h/.cpp` — 告警判断与状态机 ⭐核心

**解决什么问题**：**全项目业务逻辑最密集的文件**。原版有一个致命缺陷——`highLatched` 锁存导致"患者持续超阈值只报警一次"，这是临床上会导致**漏报死亡**的缺陷。此版本重写为完整状态机。

#### 状态机结构

```
                     条件持续成立（越过 alarmDelayMs）
        ┌──────────────────────────┐
        ▼                          │
   ┌─────────┐  用户确认   ┌──────────────┐
   │ Active  │───────────►│ Acknowledged │
   └─────────┘             └──────────────┘
        │                        │
        │ 超时未确认              │ 条件仍成立 & 超过 repeatMs
        ▼                        ▼
   ┌───────────┐          ┌───────────────┐
   │ Escalated │          │ LatchedSilent │（周期重报，绝不永久静默）
   └───────────┘          └───────────────┘
        │                        │
        └────────┬───────────────┘
                 │ 条件恢复
                 ▼
            ┌─────────┐
            │ Cleared │
            └─────────┘
```

#### 内部跟踪结构 `Track`（`AlarmDetector.h` 第 85–105 行）

每条"通道+方向"条件维护一个 `Track`：

| 字段 | 用途 |
|------|------|
| `active` | 条件当前是否成立（已越过延时） |
| `acknowledged` | 是否已人工确认 |
| `escalated` | 是否已升级 |
| `onsetMs` | 条件首次成立时刻（延时计时起点） |
| `lastReportMs` | 上次上报时刻（**重报**计时起点） |
| **`escalateAnchorMs`** | **升级计时起点（独立！）** |

**`escalateAnchorMs` 必须独立存在的原因**（`AlarmDetector.h` 第 92–97 行注释）：

> 若复用 `lastReportMs` 做升级计时，当重复周期（2s）短于升级时限（3s）时，
> 每次重报都会刷新计时器 → **升级永远无法触发**。

这是**真实的时序 Bug**，修复方式就是拆两个锚点，可作为「如何发现并修复时序缺陷」的典型案例。

#### `detect()` 主流程

```
detect(frame, configs)
 ├─ 遍历每个通道
 │   ├─ ① SQI 门控：quality < 0.35 →
 │   │      抑制生理报警 + 发 Technical 报警（第 180–203 行）
 │   │      若信号恢复 → 解除技术报警（第 205–221 行）
 │   └─ ② 上限判断 / 下限判断 → updateCondition(".../HI") / (".../LO")
 │         优先级 = levelForPriority(cfg.alarmPriority, lifeThreatening)
 └─ ③ 数据完整性：m_accumulatedDrops += frame.droppedFrames
        若 >= 阈值 → 发技术报警
```

**关键点 ①：优先级不再按"超出量程一半"折算**

第 224–231 行注释：
> 量程由显示设置决定，与临床严重度无关，折算会掩盖真实病情。
> 严重度来自"通道显式配置的优先级 + 二级阈值"。

```cpp

const bool lifeThreatening = met && cfg.hasSecondaryHigh && (s.value > cfg.alarmHigh2);

```

**关键点 ②：`m_accumulatedDrops` 必须自己累加**（第 261–267 行）

```cpp

// 稀疏丢帧将永远达不到阈值而不被上报——这正是需要避免的漏报。
```

这是第三个真实 Bug：**增量 vs 累计语义混淆**。

### 2.10 `src/core/AuditLogger.h/.cpp` — 审计追踪与持久化

**解决什么问题**：医疗器械法规（FDA 21 CFR Part 11 / IEC 62304 / MDR）要求**"谁 / 何时 / 改了什么 / 为什么"全程可追溯**，且记录应防止随意篡改。

**单例设计**：`static AuditLogger logger;`（函数内静态局部变量）——C++11 起保证**线程安全初始化**，任何模块 `AuditLogger::instance()` 即可使用，无需传递指针。

**五个事件类别**（医疗语义分离）：
| Category | 用途 |
|----------|------|
| `System` | 启动 / 停止 / 自检 |
| `Config` | 配置变更（量程 / 告警限 / 可见性） |
| `Alarm` | 生理告警（产生 / 确认 / 静音 / 解除） |
| `TechAlarm` | **技术报警**（与生理报警分离，这是 IEC 60601-1-8 的硬性要求） |
| `Data` | 导入 / 导出 / 清空 |

**落盘格式**（Tab 分隔 + 行尾 CRC32）：
```
2026-10-10T14:30:22.123+08:00  CONFIG  INFO  operator  alarmHigh  HR: 110.000 -> 100.000  3F2A1B7C
```

**CRC32 实现**（`AuditLogger.cpp` 第 13–36 行）：IEEE 802.3 多项式 `0xEDB88320`，按需查表计算。每条记录行尾附 8 位十六进制校验和 → **任何一行被改动，校验和立即不匹配**。

**诚实的范围声明**（`AuditLogger.h` 第 23–24 行注释）：
> 本项目为演示用途，校验和用于示范"完整性校验"思路，**并非密码学级别的防篡改方案**。

**为什么这句话很重要**：它体现了工程上的诚实——CRC32 防得住"意外损坏"和"随手改一个数字"，防不住"有意重算校验和"。生产级需要 HMAC + 密钥管理或者 WORM 存储。**在文档中主动写明这个边界，比宣称方案完美更能体现工程上的严谨**。

**`logConfigChange()` 专门为配置变更设计**，自动生成 `"字段: 旧值 -> 新值"` 格式，避免调用方手拼字符串不一致。

**时间戳用 `Qt::ISODateWithMs`**（第 56–60 行）：ISO 8601 带时区偏移，便于与医院 HIS/LIS 系统对齐时间基线。

### 2.16 `tests/alarm_state_test.cpp` — 自动化测试（约 280 行）

**解决什么问题**：V&V（验证与确认）需要**可重复、可自动判定**的证据，而不是"我手动点过了"。

**测试框架**：不引入 gtest/QTest，用极简自研：
```cpp
int g_fail = 0;
void check(bool cond, const QString &what) {
    if (!cond) { ++g_fail; qWarning() << "  [FAIL]" << what; }
    else       { qInfo()    << "  [ OK ]" << what; }
}
```
**退出码 = 失败用例数** → CI 中直接判定成功 / 失败。

**为什么不用 QTest**：`alarm_state_test` 目标显式 `AUTOMOC OFF`（因为该环境 `moc_predefs` 探测不可用），而 `QTest` 需要 `Q_OBJECT` → 需要 moc。自研 `check` 完全绕开这个约束。

**测试的确定性**：所有用例用 `makeFrame(idx, tsMs, ch, v, quality, dropped)` 手工构造数据 + **手动推进 `t += 100`**，完全不用真实时钟 → **永不 flaky**。

**8 个用例覆盖的状态机路径**（对照 2.7 节表格）：
1. 持续越限反复上报（修复"只报一次"的主回归测试）
2. 确认后按 `repeatMs` 重报
3. 超时未确认 → 升级（验证 `escalateAnchorMs` 独立计时的修复）
4. 500ms 毛刺被 `alarmDelayMs` 去抖抑制
5. 条件恢复 → `Cleared`
6. SQI < 0.35 → 抑制生理报警 + 发技术报警
7. 累计丢帧 → 技术报警（验证"增量累加"的修复）
8. 优先级来自 `alarmPriority` 配置而非"超出量程一半"

**每个用例都对应一个曾经真实存在的 Bug** —— 这正是回归测试的价值所在。

### 2.8 `src/core/CoordinateMapper.h/.cpp` — 坐标变换（88 行）

**解决什么问题**：项目难点 ④/⑤ —— 把"采样序号 + 生理数值"映射为画布像素，且**多通道量程不同**要独立处理。

**视口模型**：
```cpp
QRectF  m_plotRect;        // 绘图区（已排除轴/边距）
quint64 m_viewStart, m_viewEnd;              // X 视口：采样序号区间
QVector<QPair<int, Range>> m_valueRanges;    // channelId -> Y 量程
```

**两个方向的核心公式**：

```cpp
// 数值 → X 像素
double xForIndex(quint64 index) const {
    const qint64 offset = index - m_viewStart;
    return m_plotRect.left() + (double)offset / indexSpan() * m_plotRect.width();
}

// 数值 → Y 像素（注意画布 Y 轴向下，所以要翻转）
double yForValue(int channelId, double value) const {
    valueRange(channelId, minV, maxV);
    double ratio = qBound(0.0, (value - minV) / (maxV - minV), 1.0);
    return m_plotRect.bottom() - ratio * m_plotRect.height();
}
```

**`indexForX()` 反向映射**（第 78–87 行）：鼠标位置 → 采样序号，用于探针/拖拽。

**关键设计：查看控件只改视口参数，不触碰原始数据**（难点 5）。缩放平移时 `CoordinateMapper` 的 `m_viewStart/m_viewEnd` 变化，`TrendChartWidget::m_series` 的原始点**一个都不动**。这保证了：
- 缩放不失真（原始值始终可用）；
- 缩放/平移零内存分配。

**边界处理**：`setValueRange` 中 `maxValue < minValue` 时 `qSwap`；相等时 `maxValue = minValue + 1.0` 防除零；`yForValue` 用 `qBound` 裁剪防止越界画出屏幕。

### 2.9 `src/core/HistoryRecorder.h/.cpp` — 历史数据文件读写（101 行）

**解决什么问题**：支撑"历史回放"（流程 3）与"数据导出/导入"。

**文件格式**（自定义 CSV 变体，刻意选文本而非二进制，便于人工查看与调试）：
```
# vital_monitor history v1
sampleIndex,timestampMs,channelId,value
0,1728000000000,0,72.500
0,1728000000000,1,98.200
1,1728000000100,0,73.100
```

**每行一个通道值**（长表格式），而非每行一帧多列——好处是**列数固定**，增删通道不影响解析。

**`loadFrames()` 的合并逻辑**（第 73–88 行）：同一 `sampleIndex` 的多行合并回一帧：
```cpp
if (!hasCurrent || idx != currentIndex) {
    if (hasCurrent) outFrames.append(current);   // 先落上一帧
    current = SampleFrame();
    current.sampleIndex = idx; ...
}
```

**健壮性**：逐行 `trimmed()` + 跳过空行/注释/表头 + `toULongLong(&ok)` 带校验位 + 任何字段解析失败就 `continue` 跳过该行（**坏行不中断整体导入**）+ 最终文件无非空数据返回 `false` 并给 `errorMsg`。

**已知限制**：不保存 `quality` / `invalid` / `droppedFrames`。回放时这些字段默认为 1.0/false/0，意味着**回放数据看起来永远信号良好**。见审核报告 R-4。

## 四、优化空间审核（DM / 设计保证视角）

> 以下按**严重度分级**。R-1/R-2 是"工程正确性"问题，R-3 起是"锦上添花"。

### 4.1 【重要】R-1：`m_spikeCountdown[4]` 硬编码通道数

**位置**：`src/data/VitalSignSimulator.h` 第 68 行

```cpp
int m_spikeCountdown[4] = { -1, -1, -1, -1 };   // ← 写死 4
```

**风险**：若未来支持 5+ 通道（临床监护仪常配 6~8 参数：+NIBP、EtCO2、双体温），此处会**数组越界**。

**修复方案**（一处改动）：
```cpp
m_spikeCountdown.assign(m_configs.size(), -1);   // 在 start()/updateConfigs() 里 resize
QVector<int> m_spikeCountdown;                   // 成员声明改为 QVector
```
并在 `updateConfigs()` 中同步 `m_current` / `m_phase` / `m_quality` / `m_poorQualityFrames` 的长度（同样需要校验）。

**结论**：**建议修复**。改动约 10 行，消除越界风险。

---

### 4.2 【重要】R-2：`RingBuffer::removeFirst()` 是 O(n)

**位置**：`src/core/RingBuffer.h` 第 34、63、73 行

```cpp
if (m_data.size() >= m_capacity) m_data.removeFirst();   // O(n) 搬移
```

**实测影响**：容量 6 万帧时，每次 `append` 搬移 ≈ 6 万个元素（仅指针搬移 8 字节 × 6 万 ≈ 480 KB）。10 Hz 下 ≈ 4.8 MB/s 无效内存带宽。当前**完全不影响流畅度**（离 CPU 上限很远）。

**修复方案**（若追求工程完美）：
```cpp
// 用 head 下标 + 逻辑长度替代物理搬移
QVector<T> m_data;   // 物理容量 = m_capacity
int m_head = 0, m_size = 0;
// append: m_data[(m_head + m_size) % m_capacity] = v; 满则 ++m_head; ++m_size;
```
代价：`rangeByKey` 的二分查找需要在**逻辑有序视图**上做，实现复杂度显著上升。

**结论**：**可选优化，不建议现在做**。当前是"正确的简单实现"，性能已足够；贸然改环形下标会引入新的索引 Bug，收益远小于风险。**保留理由应记录在案："已知此处为 O(n)，基于实测数据与实现风险权衡后保留现状"** —— 这比盲目优化更能体现工程判断力。
